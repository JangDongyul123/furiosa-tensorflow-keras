# 10월 6일 필기 — 임베딩과 Chroma 벡터 저장소

## 1. LangChain `Document`

LangChain에서 문서를 다룰 때는 보통 `Document` 객체를 사용한다. 

핵심 필드는 다음 두 가지다.

- `page_content`: 문서 또는 청크의 실제 텍스트
- `metadata`: 출처, 파일 경로, 페이지 번호 같은 부가 정보

```python
from langchain_community.document_loaders import TextLoader

loader = TextLoader("report.txt", encoding="utf-8")
documents = loader.load()

print(documents[0].page_content)
print(documents[0].metadata)
```

`TextLoader.load()`는 대개 `Document` 객체들의 리스트를 돌려준다. 

파일 하나를 읽더라도 리스트 안에 문서가 하나 들어갈 수 있다.

## 2. 텍스트를 청크로 나누기

긴 문서를 통째로 임베딩하거나 검색에 사용하기보다, 여러 개의 작은 텍스트 조각인 **청크(chunk)**로 나누는 경우가 많다. 

검색 결과가 문서의 어느 부분과 관련되는지 좁힐 수 있고, 각 조각의 문맥도 적당한 범위로 유지할 수 있다.

```python
from langchain_text_splitters import RecursiveCharacterTextSplitter

splitter = RecursiveCharacterTextSplitter(
    chunk_size=300,
    chunk_overlap=100,
    separators=["\n\n", "\n", " ", ""],
)
chunks = splitter.split_documents(documents)
```

- `chunk_size=300`: 이 코드의 기본 길이 기준은 `len`이므로 약 300 **문자**를 뜻한다. 
토큰 300개라는 뜻은 아니다.
- `chunk_overlap=100`: 이웃한 청크가 문맥을 이어받도록 약 100문자를 겹친다.
- 구분자는 문단, 줄, 공백 순서로 자연스러운 분할 지점을 찾는다. 
- 따라서 청크 길이가 언제나 정확히 300자가 되는 것은 아니다.
- `split_documents()` 결과도 문자열이 아니라 `Document` 객체 리스트다. 
각 청크는 텍스트와 원본 출처 등의 metadata를 함께 보존할 수 있다.

청크가 너무 작으면 문맥이 부족해지고, 너무 크면 관계없는 내용이 함께 검색될 수 있다. 
적절한 크기와 겹침은 문서의 형식과 검색 목적에 맞춰 정한다.

## 3. 임베딩(Embedding)

임베딩은 텍스트를 의미적 유사도를 계산할 수 있는 숫자 벡터로 바꾸는 과정이다. 
예를 들어 `text-embedding-3-small`의 기본 설정은 문장 하나를 1536개의 숫자로 이루어진 벡터로 표현한다.

```python
from langchain_openai import OpenAIEmbeddings

embeddings = OpenAIEmbeddings(
    model="text-embedding-3-small",
    api_key=api_key,
    base_url=base_url,
)

vector = embeddings.embed_query("저는 부산에서 밀면을 먹고 싶어요.")
print(len(vector))
```

- `embed_query()`에는 문자열을 전달한다. `PromptTemplate` 객체 자체를 전달하는 것이 아니다.
- 반환값은 보통 `list[float]`이며, 설정한 임베딩 차원만큼 숫자가 들어 있다.
- 한 청크는 임베딩 모델을 거쳐 벡터 하나가 된다. 문서 청크 9개라면 개념적으로 벡터도 9개 생성된다.
- 임베딩 모델은 텍스트를 벡터로 바꾸는 모델이다. 채팅 모델처럼 자연어 답변을 작성하는 역할과 구분한다.

임베딩 API를 쓰려면 유효한 API 키와 해당 API를 제공하는 서버 설정이 필요하다. 
이 프로젝트의 예제는 `.env`에서 `MONOROUTER_API_KEY`를 읽고 MonoRouter 호환 주소를 사용한다. 키 값은 코드나 노트에 직접 적지 않는다.

## 4. Chroma에 저장하기

벡터 저장소(Vector Store)는 벡터와 원문 청크, metadata를 함께 관리하고 유사한 항목을 검색할 수 있게 한다. 
이 프로젝트에서는 Chroma를 사용한다.

```python
from langchain_chroma import Chroma

db = Chroma.from_documents(
    documents=chunks,
    embedding=embeddings,
    persist_directory="./_db/Chroma11/",
    collection_name="croma11",
)
```

흐름은 다음과 같다.

```text
원본 텍스트 파일
    ↓ Document Loader
Document(page_content, metadata)
    ↓ Text Splitter
여러 개의 Document 청크
    ↓ Embedding 모델
청크별 벡터
    ↓ Chroma
벡터 + 청크 원문 + metadata를 저장하고 검색
```

`Chroma.from_documents()`는 전달한 문서 청크를 임베딩해 컬렉션에 저장한다. `persist_directory`는 로컬 저장 위치이고, `collection_name`은 그 저장소 안에서 사용할 컬렉션 이름이다. 경로와 컬렉션 이름은 저장할 때와 다시 열 때 일치해야 한다.

## 5. 저장된 컬렉션 다시 열기

이미 만들어 둔 저장소에 연결할 때는 `Chroma`를 직접 만든다.

```python
db = Chroma(
    embedding_function=embeddings,
    persist_directory="./_db/Chroma11/",
    collection_name="croma11",
)
```

검색할 질문도 같은 임베딩 공간의 벡터로 변환해야 한다. `embedding_function`을 전달하면 검색 과정에서 질문 임베딩을 만들고 저장된 벡터와 비교할 수 있다. 
문서 저장에 사용한 것과 호환되는 임베딩 모델·차원 설정을 저장소를 열 때도 사용한다.

## 6. 유사도 검색과 Retriever

### 직접 검색

```python
results = db.similarity_search(
    "삼성전자 사업 전망을 알려줘",
    k=2,
)
```

검색 질문과 의미적으로 가까운 청크를 찾아 **`Document` 객체 리스트**로 반환한다. `k=2`는 결과를 최대 2개 요청한다는 뜻이다. 
반환값에서 실제 텍스트는 `result.page_content`, 출처 등의 정보는 `result.metadata`로 확인한다.

```python
for result in results:
    print(result.page_content)
    print(result.metadata)
```

`similarity_search()`의 기본 `k` 값은 라이브러리 구현과 버전에 따라 달라질 수 있으므로, 결과 개수를 명확히 하고 싶을 때는 `k`를 직접 지정한다. 
또한 Chroma가 항상 코사인 유사도를 쓰는 것은 아니다. 
실제 거리 기준은 컬렉션의 설정에 따른다.

### Retriever로 사용하기

Retriever는 벡터 저장소 검색을 LangChain의 공통 실행 인터페이스로 감싼 것이다.

```python
retriever = db.as_retriever(search_kwargs={"k": 2})
related_documents = retriever.invoke("삼성전자 사업 전망을 알려줘")
```

`invoke()` 결과 역시 관련 `Document`들의 리스트다. 
Retriever는 검색 단계의 구성 요소이며, 그 자체가 최종 답변을 생성하는 채팅 모델은 아니다.

## 8. 임베딩·검색·답변 생성은 서로 다른 단계

RAG는 보통 다음처럼 검색 결과를 답변 생성에 연결한다.

```text
문서 준비 → 청크 분할 → 문서 임베딩 및 저장
질문 → 질문 임베딩 → 관련 청크 검색
질문 + 검색된 청크 → 채팅 모델 → 답변
```

현재 `rag11`과 `rag12`는 주로 문서 저장과 검색까지 다룬다. 
`similarity_search()`나 Retriever가 반환한 것은 근거로 사용할 문서 청크이지, 질문에 대한 완성된 자연어 답변이 아니다. 
검색 결과를 채팅 모델에 넘겨 답변을 작성하는 단계가 추가되어야 RAG 질의응답 흐름이 완성된다.

`rag10_Embedding01.py`에는 `PromptTemplate`, `ChatOpenAI`, `StrOutputParser`를 연결하는 LCEL 예시도 주석으로 들어 있다. `StrOutputParser`는 모델 응답에서 문자열을 꺼내는 파서이고, `prompt | model | parser` 형태로 Runnable들을 연결한다. 임베딩 예제와 이 채팅 체인은 개념상 별개의 작업이다.

## 9. 실행 전 확인할 점

- 텍스트 파일 경로와 Chroma 저장 경로가 현재 실행 위치에 맞는지 확인한다. 예제에는 절대 경로와 상대 경로가 섞여 있다.
- `.env`에 `MONOROUTER_API_KEY`가 설정되어 있어야 한다. 환경변수가 없을 때 바로 `.strip()`을 호출하면 오류가 날 수 있으므로 실제 코드에서는 값 존재 여부를 확인하는 편이 안전하다.
- 저장과 로드에서 `persist_directory`, `collection_name`, 임베딩 설정을 일치시킨다.
- Chroma를 채팅 모델과 혼동하지 않는다. Chroma는 청크를 저장하고 검색하며, 최종 답변 생성은 별도의 LLM이 담당한다.
